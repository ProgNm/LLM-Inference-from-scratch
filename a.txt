# System Analysis & Architecture: "vLLM-from-scratch" Engine

This directory implements a **fully functioning, minimalist replica of the vLLM (Virtual LLM) serving engine** from scratch in PyTorch and FastAPI. It is designed to demonstrate key optimization concepts in Large Language Model (LLM) serving, specifically focusing on overcoming the memory and scheduling bottlenecks of traditional autoregressive text generation.

---

## 1. Core Architectural Bottlenecks & vLLM Solutions

Traditional LLM inference suffers from significant inefficiencies:
1. **Redundant Computation**: Generating each new token requires attending to all preceding tokens. Without caching, this leads to $O(N^2)$ computational complexity.
2. **KV Cache Memory Fragmentation**: Traditional serving systems allocate memory for the Key-Value (KV) cache contiguously for the maximum sequence length. This results in **internal fragmentation** (unused pre-allocated space), **external fragmentation** (scattered memory blocks), and **virtual memory waste** (allocations for tokens not yet generated).
3. **Static Batching Inefficiency**: Standard batching groups sequences together and runs inference until *all* sequences in the batch finish. This leads to GPU idle time (computational bubbles) while waiting for the longest sequence to complete.

This repository implements the three pillars of **vLLM** to solve these issues:
1. **KV Cache (Phase 2)**: Reuses precomputed Key and Value states to reduce attention computation to $O(1)$ per step.
2. **PagedAttention & Block Manager (Phase 3)**: Divides the KV cache into fixed-size physical memory blocks (similar to OS paging) to eliminate memory fragmentation and allow dynamic, non-contiguous allocations.
3. **Continuous Batching Scheduler (Phase 4)**: Dynamically manages sequence states, allowing new requests to join the active batch mid-flight and completed requests to leave early.

## 3. Deep-Dive: File & Component Analysis

### A. Model Module (`model/`)

#### 1. `model/transformer.py`
This file implements a custom, decoders-only GPT-style Transformer model using PyTorch.
*   **`RotaryPositionalEmbedding` (RoPE)**:
    *   Implements Rotary Position Embeddings to inject positional information directly into the Query and Key tensors.
    *   Precomputes inverse frequency vectors (`inv_freq`) using a base of 10,000 to construct rotation matrices, enabling better extrapolation to longer sequence lengths compared to absolute embeddings.
*   **`FeedForwardNetwork` (FFN)**:
    *   A multi-layer perceptron (MLP) consisting of a projection layer (`fc1` to `hidden_dim = 4 * dim`), a `GELU` activation function, a dropout layer, and a final linear layer (`fc2`) projecting back to the hidden dimension `dim`.
*   **`TransformerBlock`**:
    *   Represents a single layer of the transformer.
    *   Combines standard layer normalization (`nn.LayerNorm`), self-attention (standard `MultiHeadAttention` or `PagedAttention` depending on the `use_paged_attention` flag), and the feed-forward network with residual skip-connections.
*   **`GPTModel`**:
    *   The primary network class.
    *   Contains the token embedding lookup, position embeddings, a stack of `TransformerBlock` layers, a final layer normalization, and a language modeling head (`lm_head`) which shares weights (ties weight matrices) with the token embedding to reduce total parameters.
    *   **`generate()` method**: Implements the autoregressive generation loop. Performs temperature scaling, Top-K filtering, and Top-P (nucleus) filtering to sample the next token, updating the KV cache at each step.

#### 2. `model/attention.py`
Implements the core self-attention mechanisms.
*   **`MultiHeadAttention`**:
    *   Implements standard scaled dot-product attention ($Attention(Q, K, V) = Softmax(\frac{QK^T}{\sqrt{d_k}})V$).
    *   Features projections for Queries, Keys, and Values (`q_proj`, `k_proj`, `v_proj`).
    *   Concatenates current keys/values with historical keys/values if a `kv_cache` is supplied, enabling standard decoding.
*   **`PagedAttention`**:
    *   Designed to work with the block-based paging layout.
    *   Features a custom method `forward_with_paged_kv` that performs attention calculations using split Query, Key, and Value tensors.
    *   Note: While standard attention operations are calculated inside PyTorch, the mapping logic of these non-contiguous memory blocks is handled externally by the `BlockManager`.

#### 3. `model/kv_cache.py`
Contains models to maintain the history of keys and values across generation steps.
*   **`KVCache`**:
    *   Manages the KV cache for a single sequence.
    *   Preallocates a maximum memory buffer of shape `(batch_size, num_heads, max_seq_len, head_dim)` on the target device to avoid the overhead of dynamic GPU memory allocation.
    *   Tracks length via `cur_len` and offers `update()`, `get()`, and `reset()` utilities.
*   **`MultiSeqKVCache`**:
    *   Extends caching to multiple sequences within a batch using sequence tracking (`seq_lengths: Dict[int, int]`).
    *   Maps sequence identifiers (`seq_id`) to indices in a combined tensor block, allowing isolated updates (`update()`) and retrievals (`get()`) per active request.

### B. Engine Module (`engine/`)

#### 1. `engine/block_manager.py`
This module acts as the virtual memory management system of the vLLM engine, mapping logical token indices to physical block addresses in physical GPU/CPU memory.
*   **Constants**:
    *   `BLOCK_SIZE = 16`: Defines the block capacity (number of tokens that can reside in a single memory block).
*   **`BlockTableEntry`**:
    *   A simple data container tracking the physical `block_ids` and the `num_filled_tokens` per block allocated to a specific sequence.
*   **`BlockManager`**:
    *   Allocates, extends, and frees fixed-size blocks to prevent memory fragmentation.
    *   Maintains preallocated global cache tensors `k_cache` and `v_cache` of shape `(num_blocks, block_size, num_heads, head_dim)`.
    *   `free_blocks`: A set tracking indices of unassigned blocks.
    *   `allocated_blocks`: A map linking physical blocks to sequence IDs.
    *   `block_table`: A map from sequence IDs to their ordered lists of physical block IDs.
    *   **Core Methods**:
        *   `allocate_sequence(seq_id, num_tokens)`: Computes the number of blocks required for the sequence ($\lceil \frac{num\_tokens}{BLOCK\_SIZE} \rceil$), pops them from `free_blocks`, and maps them.
        *   `extend_sequence(seq_id, num_new_tokens)`: Allocates additional physical blocks if the current token length exceeds the sequence's existing block-level capacity.
        *   `write_to_block(seq_id, block_index, k_data, v_data, token_offset)`: Writes projected Key and Value states directly into the corresponding physical cache block.
        *   `read_from_block(...)`: Retrieves keys/values from physical block slots.
        *   `free_sequence(seq_id)`: Deallocates all blocks assigned to a sequence and returns them to the `free_blocks` pool.

#### 2. `engine/scheduler.py`
Implements the continuous batching scheduling policy.
*   **`SequenceState` (Enum)**:
    *   Defines three lifecycle states for a generation request:
        *   `WAITING`: Queued in the FIFO buffer, waiting for physical allocation and execution.
        *   `RUNNING`: Currently active in the model's execution batch.
        *   `FINISHED`: Generation complete (reached maximum tokens or produced an EOS token).
*   **`Sequence`**:
    *   Tracks request-level metadata: sequence ID, prompt string, raw input token IDs, generated output token IDs, parameters (max new tokens, temperature, top-k, top-p), and timestamp metrics.
*   **`SchedulerConfig`**:
    *   Configures serving limit bounds: `max_batch_size`, `max_seq_length`, and `max_tokens_per_batch`.
*   **`ContinuousBatchingScheduler`**:
    *   Manages the queue transitions: `waiting_queue` (FIFO list), `running_sequences` (dictionary of active sequences), and `finished_sequences` (dictionary of completed sequences).
    *   `add_sequence(...)`: Registers new requests, wraps them in a `Sequence` object, and appends them to the `waiting_queue`.
    *   `schedule_step()`: Executed at every inference iteration. Moves waiting sequences to the `running_sequences` pool as long as the concurrent batch size does not exceed `max_batch_size`. Returns the list of sequences to process.
    *   `mark_sequence_token_generated(seq_id)`: Increments the generated token count and checks if the generation limit has been reached.

#### 3. `engine/inference.py`
Orchestrates the model and engine modules into a single interface.
*   **`InferenceConfig`**:
    *   Consolidates model configuration (vocab size, dimensions, layers, heads) and engine configuration (block numbers, batch sizes, device target).
*   **`SimpleLLMEngine`**:
    *   Initializes the `GPTModel` (with `use_paged_attention=True`), the `BlockManager`, and the `ContinuousBatchingScheduler`.
    *   **Core Methods**:
        *   `add_request(prompt, tokenizer, ...)`: Encodes the prompt into tokens, registers it with the scheduler, and requests initial physical block allocation from the `BlockManager`.
        *   `_prepare_batch(sequences)`: Prepares input tensors for the step. For sequences in the prompt phase, it passes all prompt tokens. For sequences in the generation phase, it extracts only the last generated token.
        *   `generate_step()`: Executes a single scheduling-inference-decoding loop iteration:
            1. Requests active sequences from the scheduler.
            2. Builds batched input tensors.
            3. Executes the model forward pass.
            4. Samples next tokens using temperature, Top-K, and Top-P filtering.
            5. Appends the new tokens to the respective sequence outputs.
            6. Frees memory blocks and scheduler structures for sequences that have completed.
        *   `generate_all(max_steps)`: A synchronous convenience loop that executes `generate_step()` until all registered sequences are complete.

### C. Serving Module (`serving/`)

#### 1. `serving/api.py`
Exposes the inference engine as a REST API using FastAPI.
*   **Schemas (Pydantic)**:
    *   `GenerateRequest`: Prompt text, maximum generation tokens, temperature, and nucleus sampling parameters.
    *   `GenerateResponse`: A receipt returning a `request_id` and queue status (`accepted`, `running`, `completed`).
    *   `ResultResponse`: Returns the finalized text, generated token count, and performance statistics (tokens per second).
    *   `StatusResponse`: Exposes active/waiting/completed queues and block memory utilization from the block manager.
*   **Endpoints**:
    *   `POST /generate`: Accepts a text prompt, queues it in the scheduler, and returns immediately with a tracking request ID.
    *   `GET /generate/{request_id}/status`: Polls the status of a specific sequence.
    *   `GET /generate/{request_id}/result`: Retrieves the fully decoded output text once the request transitions to `FINISHED`.
    *   `GET /status`: Retrieves system-wide memory and scheduler metrics.
    *   `POST /run_inference`: Triggers the engine's background loop, processing all queued sequences until completion.
    *   `GET /health`: Standard container health check.

## 4. End-to-End Inference Lifecycle Walkthrough

To understand the interaction between these modules, here is the lifecycle of a request:

```
[Client] ---> POST /generate ---> [FastAPI serving/api.py]
                                           |
                                  Tokenize prompt (GPT-2)
                                           |
                                           v
[BlockManager] <--- Allocate Blocks <--- SimpleLLMEngine.add_request()
(Preallocates physical                               |
 token slots in memory)                              v
                                      [Scheduler] (Add to waiting queue)
                                           |
                                           v
[Client] ---> POST /run_inference --------> [SimpleLLMEngine.generate_step() Loop]
                                           |
                                           +---> 1. Scheduler selects batch of sequences
                                           |
                                           +---> 2. Prepare batched inputs (Prompt vs Decode tokens)
                                           |
                                           +---> 3. Run forward pass on GPTModel
                                           |
                                           +---> 4. Sample next tokens (Temp/Top-K/Top-P)
                                           |
                                           +---> 5. Write KV-cache updates to physical blocks
                                           |
                                           +---> 6. Check completion, free blocks if finished
                                           |
                                           v
[Client] <--- GET /generate/{id}/result <-- [FastAPI serving/api.py] (Decode & return)
```

Open Questions
IMPORTANT

Which GPT-2 variant? The plan targets gpt2 (GPT-2 Small, 117M params). Other variants exist: gpt2-medium (345M), gpt2-large (774M), gpt2-xl (1.5B). The architecture scales directly — only the hyperparameters differ. Should we hard-code Small, or make the variant configurable via a model_name parameter?

NOTE

The RotaryPositionalEmbedding class in transformer.py is not used by GPT-2 (which uses learned absolute position embeddings). It will be left in place as dead code since removing it would be a destructive change to the file's structure, but it won't affect correctness.
